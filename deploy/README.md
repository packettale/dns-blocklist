# Linux deployment

These files configure the full-catalog service behind Cloudflare Tunnel.

Use a Linux server with Node.js 24 or later, sufficient disk for raw/accepted caches, temporary partitions and two complete snapshots, and enough memory for the largest source and partition. The service example permits a 4 GiB Node heap within a 6 GiB service memory limit, with swap disabled. Measure your own catalog before selecting resources; these are instance settings rather than a future feed-size guarantee. The full public catalog exceeds 3 GB when category-group feeds are included.

1. Copy the source project to `/opt/dns-ip-blocklist`; install Node separately and verify its path. The supplied unit uses `/opt/dns-ip-blocklist-runtime/bin/node`; adjust `ExecStart` for another installation.
2. Create a dedicated `blocklist` service account. Let it read the project and write only `.cache`, `dist` and `reports`; create these directories before enabling the supplied systemd unit.
3. Put the URLhaus key in `/etc/dns-ip-blocklist/urlhaus.key`, readable only by root and the service group. Put `URLHAUS_AUTH_KEY_FILE=/etc/dns-ip-blocklist/urlhaus.key` in `/etc/dns-ip-blocklist/environment`. If authenticated GitHub reads are needed, put a least-privilege read token in that same protected environment file as `GH_TOKEN=...`. Never copy this directory into public outputs or Git.
4. Run `node --test`, then an initial local update and validation under the service account. Check source exclusions and resource use.
5. Install `dns-ip-blocklist.service` and `packettale-origin.service` in `/etc/systemd/system/`, run `systemctl daemon-reload`, and enable/start both. The updater has no listening socket. The origin runs independently as `blocklist-web`, cannot read provider credentials, and serves only public artifacts. Keep source and bootstrap files root-owned; give the updater and web account read access through `blocklist-public`. Use group `blocklist-public` with setgid mode 2750 on `.cache/snapshots` so newly built public snapshots remain readable to the origin. The web account needs traversal of the project and `.cache` parents but no read access to private cache directories. Review the updater journal for successful validations.
6. Route the Cloudflare Tunnel published hostname `blocklist.packettale.com` to `http://127.0.0.1:80`. The origin service uses that loopback address and grants only the capability needed to bind port 80. `PUBLIC_HOSTNAME` fixes the canonical HTTPS redirect destination; `REQUIRE_HTTPS=true` redirects HTTP requests forwarded by the local tunnel. Forwarded protocol headers are trusted only from loopback. Do not expose origin port 80 publicly. Caddy is not required for this tunnel deployment.
7. Install and enable `packettale-firewall.service` if this VM should accept only SSH administration, loopback, established replies, ICMP and DHCP client traffic. Its IPv4/IPv6 input chains drop other inbound traffic and leave outgoing traffic unchanged. Review the SSH exception before changing administrative access. This service does not modify cloud-provider firewalls or Cloudflare edge settings.
8. Verify the public `stats.json`, category `.txt` files, checksums and refresh behavior before loading feeds into a firewall. Check private `.cache/worker-status.json` and the systemd journal for completed update cycles; a running process alone does not establish a successful refresh.

The worker stages builds, validates them, and switches snapshots only on success. It streams downloads and supplies ETags so compatible clients can check for changes without downloading unchanged files. It never configures or applies firewall blocking policies itself.

The updater saves its active snapshot pointer atomically in `.cache/snapshots/active.json`, after validation. The separate origin checks that pointer every five seconds and serves the referenced complete snapshot. It initially uses the deployed, validated, root-owned bootstrap in `dist`. Restarting the updater revalidates its latest snapshot while the origin remains online, then waits for the persisted next daily check. At each 24-hour check it compares normalized source data against the active publication, skipping the full rebuild when unchanged. The updater never rebuilds into the active directory. Its memory/swap limits and Node runtime path must match the target VM.

Source code may live on public GitHub while this server hosts the full feeds and website. The complete catalog exceeds GitHub's regular-file and Pages site limits, so the optional manual GitHub Pages workflow refuses oversized output. The default GitHub workflow runs tests only.
